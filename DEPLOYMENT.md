# Storovex — Deployment and Verification Runbook

Storovex builds and boots with an **empty environment**. Nothing reads a credential at
module scope, so you can deploy first and add keys afterwards. This document is the
order to do that in, and how to prove each step worked.

---

## 1. Deploy with no credentials

Push to Vercel and let it build. The build does not need a single environment
variable — verified by building with every credential unset.

At this point `GET /api/health` returns `"status": "degraded"` and lists what is
missing. That is the expected state, not a fault.

---

## 2. Apply the database migrations

This is the one step that must happen before the app can serve a signed-in user.

### Route A: the Supabase SQL Editor, in small parts

**Run `00-reconcile.sql` first.** The schema uses `create table if not exists`, so a
table of the same name left over from an earlier or unrelated schema is kept as-is
and later statements then fail against it — `ERROR: 42703: column "store_id" does not
exist` is the usual symptom. The reconcile script finds any such table and drops it
**only if it is empty**; if it holds rows it changes nothing and stops with an error
naming the table, so no data is ever lost to a migration.

`00-diagnose.sql` is read-only and reports what already exists, if you want to look
before running anything.

Then paste the schema parts into the SQL Editor **in numeric order**, `01-` through
`12-`, running each before moving on. Each part depends only on the ones before it, and every part is
idempotent — if a paste is interrupted, just run that part again.

Then run `test-1-` through `test-3-` from the same directory to prove tenant
isolation, the credit-ledger invariants and billing entitlements on your own
database. They raise on any failed assertion, so completing without an error means
everything passed.

The one thing these cannot cover is the 20-way credit concurrency test, which needs
parallel connections and so will not run in a SQL editor.

### Route B: one file, for psql or the Supabase CLI

`supabase/bundle/all_migrations.sql` is the same twelve migrations concatenated in a
single transaction, with `all_tests.sql` alongside it. Better for a terminal, too
large to paste comfortably.

Everything under `supabase/bundle/` is generated by `scripts/build-sql-bundle.sh` from
`supabase/migrations/` and `supabase/tests/`. Do not edit it by hand.

### Or via psql

```sh
# Against a Supabase project you own:
for f in supabase/migrations/*.sql; do
  psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f "$f"
done
```

The connection string is in Project Settings → Database → Connection string (URI).

Apply them **in filename order** — they are numbered in dependency order and each one
depends only on files numbered before it.

**They are safe to re-run.** Verified by applying the full set three times in
succession against PostgreSQL 16 with no errors and a stable resulting schema (30
tables, 43 policies, 56 functions). If an apply fails part-way, fix the cause and run
the whole set again; you do not need to work out where it stopped.

Then prove tenant isolation actually holds on *your* database:

```sh
psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f supabase/tests/rls_isolation.sql
psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f supabase/tests/credit_ledger.sql
psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f supabase/tests/billing_entitlements.sql
```

A non-zero exit means isolation or the ledger is broken. Use a scratch project, not
one holding real data: these scripts insert fixture users and stores.

## 3. Set the required variables, then verify

In Vercel → Project Settings → Environment Variables:

```
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
SUPABASE_SERVICE_ROLE_KEY     # server-only, bypasses RLS
NEXT_PUBLIC_SITE_URL          # absolute origin, no trailing slash
CRON_SECRET                   # any long random string
```

Redeploy, then run the preflight:

```sh
node scripts/verify-integrations.mjs https://your-app.vercel.app
```

Every check is a **read**. Nothing is sent, charged, or generated.

```
  [PASS] Supabase     Connected; schema and seed data present.
  [SKIP] Paddle       Not configured: PADDLE_API_KEY, PADDLE_WEBHOOK_SECRET
  [SKIP] Resend       Not configured: RESEND_API_KEY, RESEND_WEBHOOK_SECRET
  ...
```

Anything marked FAIL prints a concrete remedy underneath it.

## 4. Add the rest, one at a time, verifying each

Order matters less than verifying as you go.

### Gemini — image generation
```
GEMINI_API_KEY
GEMINI_IMAGE_MODEL     # optional; defaults to gemini-2.5-flash-image
```

Re-run the verifier. It calls Google's ListModels and confirms **the configured model
actually exists for your key**. This matters: Google validates the API key *before*
the model name, so an invalid-key probe can never catch a wrong model name. If the
default model is not available to you, the check names the ones that are.

### Resend — transactional email
```
RESEND_API_KEY
RESEND_WEBHOOK_SECRET      # from the Resend webhook settings (Svix signing secret)
RESEND_FROM_EMAIL          # must use a domain verified in Resend
```

The verifier reads your domain list and fails if the `from` domain is not verified.
Resend accepts a send from an unverified domain and then **silently fails to
deliver** — much harder to diagnose than an outright rejection.

Point the Resend webhook at `https://your-app/api/email/webhook`.

### Paddle — billing
```
PADDLE_API_KEY
PADDLE_WEBHOOK_SECRET
PADDLE_ENVIRONMENT=sandbox      # switch to live only when you are ready
PADDLE_PRICE_STARTER_MONTHLY    # one id per plan and cycle
PADDLE_PRICE_STARTER_ANNUAL
PADDLE_PRICE_MID_MONTHLY
PADDLE_PRICE_MID_ANNUAL
PADDLE_PRICE_PRO_MONTHLY
PADDLE_PRICE_PRO_ANNUAL
```

The verifier lists your prices and fails if a configured id does not exist in that
environment. **Price ids differ between sandbox and live**, so this is the check that
catches a half-finished switch to production.

Point the Paddle webhook at `https://your-app/api/billing/webhook`.

### Chat providers — optional
```
CEREBRAS_API_KEY / OPENROUTER_API_KEY / ANTHROPIC_API_KEY
```

## 5. Schedule the job worker

Generation jobs are queued by the API and executed by a worker. Nothing runs them
until something calls the worker endpoint. Add to `vercel.json`:

```json
{
  "crons": [
    {"path": "/api/jobs/process", "schedule": "* * * * *"}
  ]
}
```

Vercel cron sends `Authorization: Bearer $CRON_SECRET` automatically when the variable
is set. Without `CRON_SECRET` the endpoint refuses every request — an open endpoint
that spends user credits would be worse than a broken one.

---

## 6. First real end-to-end run

The offline test suite proves our parsing is correct *given* each provider's
documented response shape. It cannot prove a key works or a model exists. Do this once
before trusting the pipeline:

1. Sign up, confirm the email, sign in.
2. Create a store and a project.
3. Upload one reference photo.
4. Start a generation.
5. Watch `GET /api/generation/status?jobId=...` reach `completed`.
6. Check the credit balance fell by the estimated amount, and that `credit_ledger` has
   a `reservation` and a matching `commit`.
7. Force a failure — set `GEMINI_IMAGE_MODEL` to something invalid — and confirm the
   job dead-letters and the credits come **back**.

Step 7 is the one worth doing deliberately. A refund path that has never run is a
refund path you do not have.

---

## What is verified, and what is not

**Verified against live APIs:** the Gemini and Anthropic endpoint URLs, request
shapes, headers and error classification — probed with a deliberately invalid key.
This caught a real bug: Google reports a bad key as HTTP **400**, not 401, so it was
being classified as a malformed request.

**Verified against PostgreSQL 16:** all 12 migrations apply from scratch and are
re-runnable; tenant isolation, credit-ledger invariants, 20-way credit concurrency,
and billing entitlements all pass.

**Not verified:** no successful authenticated call has been made to any provider, and
no email has been sent or payment taken, because no credentials are configured. The
`verify-integrations` preflight exists to close that gap in one command the moment
they are.
